# Bounded MKV source-reader correction

The owner's 2103508 failure is source-reader exhaustion after confirmed receiver playback. The owner's exact source bitrate and phase-by-phase read counters were unavailable. It is not evidence that hardware conversion ran: the recorded selection was `receiver_capability_unknown` direct playback.

The failure mechanism was reproduced using the original source-reader implementation and pinned FFmpeg 6.0.1: interleaved video bytes are scanned repeatedly while constructing canonical AAC windows, seeking from sparse audio indexes and recovering video decode timestamps. The old 32 MiB allowance covered every pass rather than just the delivered fragment. A 24-second, approximately 14 Mbps fixture produced fragments under 8 MiB but exhausted that allowance on a later/cold request. A bounded observational host run measured 65,271,291 source bytes; verified video-cue seeking reduced the same request to 51,750,554 bytes. This establishes an implementation defect without assigning an unmeasured exact read breakdown to the owner's stream.

The five-file correction uses verified video cues for the existing AAC warmup target and avoids unnecessary next-GOP scanning only at independently decodable AVC IDR / HEVC IDR_N_LP boundaries. It preserves HEVC leading-picture handling. A planner models the actual two-window AAC cache, origin clock anchor and repeated source passes, using validated cue byte extents. It installs one checked allowance per serialized request: 32 MiB floor, 128 MiB hard ceiling. Excessive working sets are rejected; seeks never replenish the quota. Unknown cue extents retain the old bounded behavior. The existing time, packet, output and cancellation limits remain.

Sanitized diagnostics report fragment index, read budget, consumption, seek/range counts, AAC/preroll/selected/lookahead phases and budget exhaustion. They contain no media URLs, headers, cookies or credentials. Planner errors cannot be masked by a prior request's exhausted budget.

Focused host checks passed sequential, cold, random and cache-regenerated requests; deterministic output; exact video packet bytes and timestamps; AAC timeline/alignment; ceiling and cancellation negatives. Production Cast DEX passed the component/JNI gate (44065804643). The ARM64 library compiled and linked using the original Kodi engine. Actual Android private-relay/HLS testing exercised continuation, random seeking, authenticated HTTP ranges and cancellation with zero remaining native contexts.

Android execution run 44067382846 failed its result-wrapper JSON transport after the actual tests completed. This failure is retained. Read-only recovery run 44071299408 passed independent verification of the mandatory complete results and retained media without rebuilding or rerunning the app: 576 video packets matched source bytes and presentation timestamps; 1,125 AAC packets retained the sample grid and decoded. This distinction is part of the release evidence.

Unsigned stage 44072633619 passed: candidate 2103510 changes four APK members, leaving 7,773 unchanged; recovery 2103511 restores 2103508 and changes only two version metadata members, leaving 7,775 unchanged. All 1,026 unaffected Cast classes remain identical. The sole new obfuscated Cast class has explicit Infinity ownership. Signing, original certificate, registered owner payload and install-over checks are separate release gates.

Physical TV continuity, source-network throughput, Return to Phone and owner acceptance remain pending. Neither the incident nor these tests establishes hardware-video performance. No shutdown, Cobra, provider, tracking, settings, profile or other Infinity implementation is changed.
