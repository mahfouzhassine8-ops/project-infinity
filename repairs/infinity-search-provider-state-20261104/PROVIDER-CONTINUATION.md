## Concrete new finding: WatchNixtoons2 can invalidate its own search

Recovered the exact previously reviewed WatchNixtoons2 **0.14.24** archive and verified the eight source hashes in signed 453's `NAVIGATION-CONTRACTS.json`. These source bytes implement the existing accepted `nixtoons-query-search-v1` adapter. This is reference/contract evidence, not a claim that the phone's current version was collected.

The TV route supplies `action=actionSearchMenu`, `path=/search`, `searchType=series` and an explicit `query`.

1. `lib/plugin.py:511–545`, `actionSearchMenu`, accepts the supplied query without opening a keyboard.
2. Lines 538/540 call `ADDON.setSetting('searchHistory', ...)` **before** `actionCatalogSection` produces results. This occurs for every nonempty query, including repeated queries.
3. `lib/network.py:49–112`, `request_helper`, also writes `requestTimes` after the network response. This stores rate-limiting history; it is a second independent settings-file change.
4. Preserved Kodi `interfaces/legacy/Addon.cpp:129–138` calls `SaveSettings()` after the Python setting update. `addons/Addon.cpp:699–773` serializes, saves and confirms the settings file under its existing persistence protections. No change to that durability path is proposed.
5. Infinity `_provider_result` compares the whole before/after `_query_signature`. A settings-file stamp change triggers `state_changed`; `_publish_result` discards rows and shows the reported message.

Thus a normal search side effect is being treated as a potentially invalidating external change. The source route has a real incompatibility with the whole-file validation rule: a completed result can be rejected without a new query, source update, profile switch or cancellation. Retrying is not a reliable remedy because it writes history again. Do not disable history, timing storage or persistence to avoid this.

Seven new host cases execute only extracted, hash-checked publisher functions with synthetic Android/settings/network boundaries. The real shipped Infinity validation functions run unchanged. Fresh and repeated Nixtoons queries reproduce rejection; the network-timing write independently reproduces it. No real network search or Kodi provider was launched. These passing diagnostic assertions reproduce a defect; they are **not** passing acceptance tests for a repaired product.

## Crew has distinct conditional paths

Recovered exact Crew plugin **3.2.2** and its reviewed dependency **3.2.26**, matching the previous archive/source hashes. The module's old moving-branch URL now returns 404; its original GitHub commit still contains the identical archive. No access restriction was bypassed.

- The verified receiver `TVShows.search_term` (`tvshows.py:506–523`) writes search history to SQLite, then calls `get(search_url)`. That database is not part of `_query_signature`. A host check using real disposable SQLite confirms this write alone leaves the result accepted.
- `thecrew.py:23–33` calls `settings_repair.repair_if_needed` before importing the runtime/router. `settings_repair.py:1514–1552` can restore or normalize settings; its sanitization path can restore credentials. These are potentially meaningful changes, so they cannot be globally ignored. This path was read, **not executed** against a user profile.
- `CrewRuntime.__init__ → initialize_all → check_orion` (`crewruntime.py:807–915,1188–1220`) conditionally writes installation/account-status settings. Extracted-function tests show no writes when that integration is absent, and state rejection after status writes when present or when its lookup fails. The lookup and integration state are synthetic; this does not assert that Orion is installed, enabled or involved on the user's phone.
- Other legitimate settings writers exist, including token refreshes. No private account settings or installed provider data were inspected.

The original Crew adapter pins the entrypoint, dependency manifest/router and reviewed receiver sources. Conditional helper behavior is reference evidence only: helper versions and the actual state delta on the phone remain uncollected. Do not generalize the Nixtoons cause to Crew or guess an account failure.

## Smallest safe correction plan and remaining gate

The smallest architectural correction is in the existing universal Search validation path: separate **cache freshness** from **the validity of the current owned response**, while preserving source/dependency/profile/query/cancellation checks and meaningful settings changes. Do not remove the whole guard, reissue providers automatically, globally ignore settings.xml or accept cached results under a new signature.

For a contract-bound nonsemantic-field approach, Nixtoons' history and request-timing fields are now identified by source. That is not yet a complete safety proof: accepting a changed file on two semantic endpoint snapshots alone can conceal intervening configuration changes or another writer. A passing end-state comparison is not proof of write ownership. Crew's settings repair demonstrates why broad exclusions are unsafe. Native write-ownership changes would require separate authorization because native 2103453 is frozen.

Before a production change, capture one bounded failing session using the existing request lifecycle. The missing evidence is precise:

- actual installed provider/dependency versions and verified adapter family/source identity;
- original native status before any Python `state_changed` replacement;
- cache hit versus fresh RPC, cancellation/overlap state and elapsed time;
- changed-component reason mask: provider/dependency settings, manifest, profile, Continue Playing or global revision;
- if settings changed, a privacy-safe distinction between a known search bookkeeping write and a meaningful configuration/credential change.

The diagnostic should reuse already-read signature components, remain bounded to the selected requests, and never log queries, media paths, URLs, raw request tokens, settings values, credentials or result titles. It must not run providers twice, add workers or modify the rejection decision. No such hook has been deployed. No compatible connected Android target is exposed in this environment.

**Current decision:** confirmed self-invalidation mechanism for the verified Nixtoons route; conditional Crew mechanisms and exact phone attribution remain unresolved. Production correction is held at the safety gate. This is not a claim that either reported failure has been fixed.
